# MiniAgent

[![CI](https://github.com/GolovkoStepan/mini_agent/actions/workflows/ci.yml/badge.svg)](https://github.com/GolovkoStepan/mini_agent/actions/workflows/ci.yml)

Минимальный кодовый агент на Ruby: получает задачу, планирует шаги, выполняет shell-команды через LLM с поддержкой tool calling и возвращает результат.

Работает с любым OpenAI-совместимым эндпоинтом `/chat/completions` — LM Studio, Ollama, vLLM или облачный провайдер.

## Установка

```bash
git clone https://github.com/GolovkoStepan/mini_agent.git
cd mini_agent
bin/setup
```

Или как гем:

```bash
gem build mini_agent.gemspec
gem install ./mini_agent-0.2.0.gem
```

### Адрес LLM-сервера

По умолчанию агент обращается к хосту `llm-server` на порту 1234. Если сервер
стоит на отдельной машине, пропишите её адрес в `/etc/hosts`:

```
192.168.1.10	llm-server
```

Если сервер запущен на той же машине — укажите петлевой адрес:

```
127.0.0.1	llm-server
```

Имя выбрано односоставным намеренно: зону `.local` на macOS перехватывает
mDNSResponder, и записи в `/etc/hosts` там срабатывают ненадёжно.

Правку `/etc/hosts` можно не делать — тогда задавайте адрес явно через
`--base-url` или `LLM_BASE_URL` (см. ниже).

## Использование

```bash
# разовая задача
mini_agent "найди все TODO в проекте и покажи их списком"

# интерактивный режим — история диалога сохраняется между задачами
mini_agent -i

# указать сервер и модель
mini_agent --base-url http://localhost:1234/v1 --model qwen3-coder "запусти тесты"
```

Из репозитория без установки гема:

```bash
bundle exec ruby -Ilib exe/mini_agent "задача"
```

### Опции

| Опция | Описание |
|---|---|
| `-i`, `--interactive` | Интерактивный режим |
| `--max-turns N` | Максимальное число ходов (по умолчанию 50) |
| `--max-tokens N` | Максимум токенов в ответе модели (по умолчанию половина окна, но не больше 16384) |
| `--context-window N` | Размер контекстного окна модели в токенах |
| `--llm-timeout N` | Ожидание ответа модели в секундах (по умолчанию 1200) |
| `--[no-]stream` | Показывать ответ по мере генерации (по умолчанию включено) |
| `--[no-]auto-compact` | Сворачивать диалог самостоятельно, когда кончается окно (по умолчанию включено) |
| `--compact-at N` | С какой доли занятого окна считать, что место кончается (0.75) |
| `--[no-]markdown` | Разметка в ответах модели (по умолчанию включена) |
| `--retry-count N` | Число попыток при ошибке сети (3) |
| `--retry-delay N` | Задержка между попытками в секундах (2) |
| `--base-url URL` | Адрес LLM-сервера |
| `--model NAME` | Имя модели |
| `--list-models` | Показать модели, загруженные на сервере |
| `--cwd DIR` | Рабочий каталог для команд агента |
| `--log FILE` | Писать транскрипт диалога в файл (JSONL) |
| `--resume` | Продолжить последнюю сессию этого каталога (или журнал из `--log`) |
| `--[no-]session` | Сохранять сессию в `~/.mini_agent/sessions` (по умолчанию включено) |
| `--settings FILE` | Файл настроек вместо `~/.mini_agent/settings.json` |
| `--no-settings` | Не читать файл настроек вовсе |
| `--temperature N` | Разброс при выборе следующего токена |
| `--top-p N` | Отсечение по накопленной вероятности |
| `--top-k N` | Сколько кандидатов рассматривать |
| `--min-p N` | Порог вероятности относительно лучшего кандидата |
| `--repeat-penalty N` | Штраф за повтор (llama.cpp, LM Studio; нейтраль 1.0) |
| `--presence-penalty N` | Штраф за повтор в стиле OpenAI (нейтраль 0) |
| `--frequency-penalty N` | Штраф за частоту в стиле OpenAI (нейтраль 0) |
| `--seed N` | Зерно генератора: два прогона с одним зерном совпадают |
| `--sampling PAIRS` | Те же восемь параметров одной строкой: `--sampling top_k=50,temperature=0.3` |
| `--policy NAME` | Когда спрашивать подтверждение: `deny`, `ask`, `unsafe` (по умолчанию `deny`) |
| `--plan` | Режим планирования: только чтение, в ответе — план |
| `--[no-]allow-unsafe` | То же, что `--policy unsafe` |
| `-v`, `--version` | Версия |

### Коды возврата

| Код | Что произошло |
|---|---|
| 0 | Задача выполнена |
| 1 | Ошибка употребления: неверная опция, нет задачи, несуществующий каталог |
| 2 | Не удалось открыть соединение — сервер не отвечает или адрес неверен |
| 3 | Сервер ответил отказом, и задача не сделана (например, переполнен контекст) |
| 4 | Кончились ходы (`--max-turns`) или агент зациклился — задача может быть не доделана |

Коды 2 и 3 различаются намеренно: в первом случае сервера нет вовсе, во втором
он ответил, но запрос отклонил. Код 4 отделён от них по той же причине: там
что-то сломалось, здесь всё работало исправно — просто не хватило отведённых
ходов. Повторять с теми же настройками имеет смысл только в первых двух
случаях. Интерактивный режим всегда завершается нулём — провал отдельной
задачи не есть провал сессии.

### Инструменты

Модели доступны четыре инструмента; полный список с описаниями печатает
`/tools`.

| Инструмент | Что делает |
|---|---|
| `bash` | Выполняет команду в оболочке |
| `read_file` | Читает файл целиком |
| `write_file` | Пишет файл целиком: создаёт или заменяет |
| `edit_file` | Заменяет один точный кусок текста другим |

Всё это умеет и `bash` — тем не менее файловые инструменты заведены отдельно,
и не ради удобства. Запись файла через heredoc — это генерация длинного текста
внутри аргумента команды: кавычка, обратная косая или строка, совпавшая с
ограничителем, ломают файл молча. `sed -i` и heredoc обе умеют сделать
наполовину и вернуть код `0`, после чего модель докладывает об успехе, а в
файле лежит то, чего никто не писал.

`edit_file` требует, чтобы `old_text` встречался в файле **ровно один раз**.
Найденное дважды — отказ, а не выбор первого попавшегося: первое попавшееся
невозможно проверить по результату, и ошибка вылезет через десяток ходов
в чужом месте. Правка либо применяется целиком, либо не применяется вовсе,
и об этом сказано вслух.

`read_file` не добавляет номера строк, хотя они напрашиваются: `edit_file`
ищет текст дословно, и модель, увидевшая файл с номерами, вставила бы их
в `old_text`.

Политика подтверждений и режим планирования действуют и здесь, причём точнее,
чем на `bash`: инструмент сам говорит охране, читает он или пишет, — это не
приходится угадывать разбором строки. Отказывать чтению по недоразумению
(как `find` в режиме планирования) тут не из-за чего.

### Параметры сэмплинга

Как модель выбирает следующий токен. Задавать их необязательно: **что не
задано, того в запросе нет вовсе** — решает пресет, выбранный на сервере.

```bash
mini_agent --temperature 0.3 --top-k 50 --repeat-penalty 1.12 "задача"
mini_agent --seed 1 "задача"          # два прогона подряд дадут один ответ
```

Действующие значения показывает `/model`, и они же пишутся в заголовок сессии
журнала (`--log`): настройка определяет поведение прогона целиком, а
ретроспективно её не переспросить.

Отсутствие поля в запросе — это способ сказать «решает сервер», и он не
равнозначен отправке умолчания. Пока агент клал в каждый запрос зашитую
`temperature: 0.1`, выставленное на сервере значение не применялось ни разу:
поле в теле запроса перебивает пресет.

**Штрафы за повтор — три разные величины, а не три названия одной.**

| Поле | Кто понимает | Нейтральное значение | Как действует |
|---|---|---|---|
| `repeat_penalty` | llama.cpp, LM Studio, Ollama | `1.0` | Делит логиты |
| `frequency_penalty` | OpenAI и совместимые | `0` | Вычитает пропорционально частоте |
| `presence_penalty` | OpenAI и совместимые | `0` | Вычитает за сам факт появления |

`1.12` в поле `frequency_penalty` означало бы почти максимальный штраф там, где
просили слабый. Поэтому агент не переводит одно в другое и шлёт ровно то поле,
которое названо флагом; vLLM ту же величину зовёт `repetition_penalty` —
своей таблицы переводов агент не заводит.

Диапазоны не проверяются: у каждого сервера они свои, и неподходящее значение
покажет сам сервер ответом 400. А вот нечисло (`LLM_TEMPERATURE=abc`) роняет
запуск сразу: молча превратить его в `0.0` значило бы работать не с той
настройкой, которую задали.

`min_p` в документации LM Studio не перечислен — если результат при `--min-p 0.05`
и `--min-p 0.95` неотличим, сервер это поле игнорирует.

#### Одной строкой: `--sampling`

Подобранный набор длиннее строки терминала, а в скриптах он ещё и повторяется.
`--sampling` принимает те же восемь имён парами:

```bash
mini_agent --sampling top_k=50,temperature=0.3 "задача"
mini_agent --sampling "min_p=0.05 repeat_penalty=1.12" "задача"
mini_agent --sampling top_k=50 --sampling temperature=0.3 "задача"   # флаг можно повторять
```

Пары разделяются запятой или пробелом, **дробная часть пишется через точку**:
`temperature=0,3` разрежется по запятой пополам, и обломок `3` вызовет отказ.

Имена ключей — те же, что у флагов выше, и проверяются по списку: `temperatur=0.3`
роняет запуск с подсказкой ближайшего имени. Проверка тут не украшение, а условие,
при котором общая форма вообще заводится: неизвестное поле сервер молча
игнорирует, и опечатка выглядела бы работающей настройкой.

Один параметр, заданный дважды — и повтором внутри `--sampling`, и вместе
с отдельным флагом, — тоже отказ: указания противоречат друг другу, и ни одно
не точнее другого. Во всём остальном разложенная пара неотличима от именованного
флага: она так же перебивает переменную окружения и файл настроек.

### Повтор одного и того же вызова

Модель иногда упирается: выдаёт один и тот же вызов с теми же аргументами
ход за ходом, получая тот же результат. Само по себе это не проходит, а стоит
каждый раз настоящего запроса и места в контексте.

Агент считает одинаковые вызовы **подряд** и вмешивается на двух уровнях:

```
● Bash(grep -rn VERSION spec/)
● Повтор вызова: команда та же — не выполняется, модели возвращён прежний результат.

● Bash(grep -rn VERSION spec/)
● Тот же вызов третий раз подряд — агент зациклился, задача остановлена.
```

На **втором** вызове подряд команда не выполняется: модель получает прежний
результат с припиской, что команда уже выполнялась, ничего не изменилось
и надо сменить подход. Сразу обрывать нельзя — одиночный повтор бывает
осмысленным. На **третьем** задача останавливается с кодом возврата `4`:
приписку модель может и не прочесть, и третий уровень существует ровно
на этот случай.

Команды сравниваются дословно, без нормализации: повтор с переставленным
пробелом не заметится. Ошибка в эту сторону дешевле — лишний холостой ход
против оборванной живой задачи. Счёт ведётся внутри одной задачи: в
интерактивном режиме одна и та же команда в двух разных задачах повтором
не считается.

### Интерактивный режим

`mini_agent -i` держит одну историю на всю сессию: следующая задача видит
результаты предыдущей. Стрелка вверх поднимает прошлые задачи, строку можно
править по месту (`Reline` из stdlib).

| Команда | Что делает |
|---|---|
| `/help` | Список команд |
| `/clear` | Начать историю заново |
| `/context` | Из чего складывается контекст |
| `/compact` | Свернуть диалог в резюме |
| `/init` | Создать описание проекта (`AGENTS.md`) |
| `/plan` | Режим планирования: сначала план, потом работа |
| `/model` | Какая модель, сервер, каталог и журнал используются |
| `/tools` | Доступные модели инструменты |
| `/usage` | Расход токенов за сессию |
| `/exit` | Выход (`exit` без слэша тоже работает) |

`/clear` нужен, когда следующая задача не связана с предыдущей: история
накапливается и уходит модели целиком, а лишний контекст и стоит токенов, и
сбивает с толку.

### Режим планирования

Сначала план, потом работа. В режиме планирования агент изучает проект, но
ничего в нём не меняет: выполняются только заведомо читающие команды, а всё
остальное отвергается, не доходя до запуска. В конце он отвечает планом
и спрашивает, выполнять ли его.

```
> /plan
Режим планирования включён: только чтение, в конце — план. Повторный /plan выключает его.

> добавь классу Greeter метод farewell

● Bash(ls)
  ⎿ greeter.rb

● Bash(cat greeter.rb)
  ⎿ class Greeter
      def call = "привет"
    end

● Вот план:
  1. В greeter.rb после метода call добавить `def farewell = "пока"`.

План сохранён: ~/.mini_agent/plans/2026-08-19-1832-добавь-классу-greeter-метод-farewell.md

Выполнять этот план? (y — да, e — правка в редакторе, N — нет): y
План принят. Режим планирования выключен, выполняю.
```

Согласие выключает режим и отправляет план модели её же словами — план
повторяется целиком, потому что между планированием и одобрением могло
пройти сворачивание диалога. Отказ оставляет режим включённым: план
уточняют следующей задачей.

**`e` открывает план в `$EDITOR`.** План почти всегда верен на три четверти,
и без правки остаётся либо принять его целиком, либо отвергнуть и переписывать
задачу словами в надежде, что модель поправит именно тот пункт. Редактор
открывается на уже записанном файле, а после выхода из него план перечитывается
с диска целиком — **файл, а не память агента, и есть источник истины**.

```
Выполнять этот план? (y — да, e — правка в редакторе, N — нет): e
Открываю план в nano: ~/.mini_agent/plans/2026-08-19-1832-добавь-классу-greeter-метод-farewell.md
План перечитан из файла.
Выполнять этот план? (y — да, e — правка в редакторе, N — нет): y
```

Вопрос задаётся снова: открыть план в редакторе — не то же самое, что одобрить
его, и «поправил, перечитал, передумал» остаётся возможным. Опустевший файл
считается отказом — то же соглашение, что у `git commit`. Редактор берётся из
`VISUAL`, затем из `EDITOR`; своего умолчания нет намеренно — `vi` запирал бы
в себе того, кто не знает, как из него выйти, поверх уже составленного плана.

**История планирования при этом выбрасывается.** Выполнение начинается с
чистого контекста: системный промпт, описание проекта, каталог — и одобренный
план. Всё, что агент прочитал, пока изучал проект, в окно больше не входит;
план и есть готовое резюме этого изучения, только структурированное и
одобренное человеком. Сворачивать историю моделью здесь незачем — это стоило
бы хода и дало бы ещё один шанс нафантазировать.

**План пишется в файл** `~/.mini_agent/plans/` до того, как задан вопрос:
«нет» означает «не выполнять», а не «выбросить». Имя файла — дата, время и
начало задачи; русские имена не транслитерируются. Каталог создаётся с правами
`0700`, файл — `0600`. Если записать не удалось, печатается предупреждение,
но работа продолжается: план нужен человеку, и потеря файла не отменяет уже
проделанного.

Файл пишется самим агентом на Ruby, в свой каталог, по явному указанию
человека, — запрет режима это не нарушает: запрещено то, что модель делает
командой в проекте.

Это не то же самое, что `--policy ask`. Подтверждения по одной команде
показывают дерево, а не лес: согласиться на десять невинных шагов и увидеть
замысел целиком только на одиннадцатом. Здесь замысел показывают целиком
и до того, как что-то произошло.

Разовый запуск печатает план и выходит, ничего не выполнив, — одобрять
в скрипте некому:

```bash
mini_agent --plan "перенеси конфигурацию в YAML"
```

Что делать нельзя, знает тот же список читающих команд, что и политика `ask`
(см. «Безопасность»), — со всеми его границами. Это значит, что `find`,
перенаправление и `2>/dev/null` в режиме планирования отвергаются, хотя
ничего и не пишут; модели об этом сказано прямо, вместе с заменой (`ls`,
`grep`, `git ls-files`), чтобы она не открывала это для себя отказами.
И это значит главное: **песочницей режим не является**. Разбирается строка,
а не дерево команд, и `bash -c`, переменная или base64 обходят его так же,
как обходят денилист. Режим защищает от самодеятельности модели, а не
от злого умысла; от второго защищает только изоляция.

`/init` в этом режиме не работает: он пишет файл. Агент говорит об этом
сразу, а не после того, как потратит полдюжины ходов на изучение проекта.

### Что занимает контекст

`/context` показывает, из чего сложился диалог:

```
> /context
Контекст: 7 сообщений

  системный промпт        908 знаков   41%
  описание проекта        390 знаков   18%
  задачи                   26 знаков    1%
  ответы модели             471 знак   22%
  результаты команд       395 знаков   18%
  ------------------------------------
  всего                  2190 знаков

  по данным сервера последний промпт — 955 токенов
```

**Размер в знаках, а не в токенах, и это сделано намеренно.** Своего
токенизатора в агенте нет, а пересчёт знаков в токены коэффициентом даёт
ошибку в полтора-два раза (для русского текста и для кода он разный) — и при
этом выглядит ровно так же уверенно, как измерение. Знаки посчитаны точно;
единственное честное число о токенах присылает сервер в `usage`, и оно
показано отдельной строкой как есть. Если сервер `usage` не присылает, агент
говорит об этом, а не печатает ноль.

Описание проекта вынесено отдельной строкой не для красоты: `AGENTS.md`
попадает в системный промпт и переживает и `/clear`, и `/compact`. Если место
занято им, `/context` предупредит — уменьшить его можно только правкой файла.

Вывод команды, уходящий модели, тоже ограничен, и потолок считается от окна:
четверть того, что остаётся истории после резерва под ответ, но не больше
10 000 знаков. Одно фиксированное число не может быть верным и при окне 8192,
и при 50176 — в первом случае единственный `cat` большого файла съедал бы
половину окна. Показанный на экране кусок ограничен отдельно и другим числом:
там речь о читаемости консоли, а не о контексте.

### Сворачивание диалога

`/compact` просит модель пересказать диалог и заменяет им историю:

```
> /compact
Диалог свёрнут: 4625 знаков → 2469.
```

Резюме встаёт на место всего разговора; системный промпт и описание проекта
возвращаются в новую историю целиком. Модель после этого помнит, что было
сделано, но не дословные формулировки — поэтому сворачивать лучше на границе
между задачами, а не посреди одной.

**`/compact` работает на упреждение и переполненный контекст не лечит.** Чтобы
получить резюме, историю надо отправить модели целиком — то есть сделать ровно
тот запрос, который при упоре в окно уже не проходит. Звать его нужно до того,
как стало тесно; `/context` показывает, когда пора.

Если свернуть не удалось — сервер недоступен, модель вернула пустой ответ,
нажали Ctrl+C — история остаётся прежней и работать можно дальше. Потерять
диалог, не получив взамен резюме, — худший из исходов, и агент его избегает.
Запрос на сворачивание оплачивается и попадает в `/usage`, даже если резюме
не пригодилось.

#### Автоматическое сворачивание

Звать `/compact` вручную нужно не всегда: когда окно заполняется на три
четверти, агент сворачивает диалог сам — на том же упреждении и по тому же
порогу, по которому `/context` советует это человеку.

```
● Bash(head -n 200 CHANGELOG.md)
  ⎿ ## [Unreleased]
    … +109 строк
● Окно заполнено на 219% — сворачиваю диалог, чтобы работа не оборвалась.
Диалог свёрнут: 11339 знаков → 2100.

● Bash(find lib/mini_agent -type f | wc -l)
  ⎿       40
```

Работает это и посреди задачи, и между задачами в интерактивном режиме.
Выключается `--no-auto-compact` или `AUTO_COMPACT=false`.

Сворачивание посреди задачи не бесплатно: модель помнит, что было сделано,
но не дословно, и после него ответ бывает суше и короче, чем был бы без.
Это плата за то, что работа вообще продолжилась, — но если задача длинная
и известно, что окно кончится, дешевле разбить её на части самому.

Агент сдаётся до конца сессии — и говорит об этом вслух, — если сворачивать
бесполезно: резюме не получилось, оно вышло не короче диалога, освободило
меньше пятой части или окно занято описанием проекта, которое сворачивание
не трогает вовсе. Теснота сама по себе не проходит, так что без этого он
упирался бы в ту же стену каждый ход, тратя на неё по запросу.

Заполнение меряется по последнему ответу сервера, то есть с отставанием на
один ход, а сразу после сворачивания — не меряется вовсе, пока не придёт
новый `usage`. Поэтому порог и стоит на 75%, а не на 95%.

Порог настраивается: `--compact-at 0.6` или `AUTO_COMPACT_AT=0.6`. Три
четверти выбраны под запас на один ход вслепую, а не под качество ответов —
небольшие сети начинают путаться заметно раньше, и правильное для конкретной
модели число должны показать оценочные задачи (`make evals`), а не догадка.

#### Напоминание о задаче

По тому же порогу агент делает ещё одно: когда окно заполнено, он повторяет
исходную задачу отдельным сообщением перед запросом. На экране это никак не
проявляется — сообщение адресовано модели, а не человеку; в журнале (`--log`)
оно видно наравне с остальными.

Задача сказана один раз и уезжает вверх истории. К двадцатому ходу между ней и
текущим запросом лежат десятки выводов команд, и модель отвечает уже им, а не
поручению: придумывает недостающее, объявляет сделанным соседнее, берётся за
то, чего не просили. Задача повторяется дословно — пересказ пришлось бы у
кого-то спрашивать, то есть тратить ход и давать ещё один шанс нафантазировать.

Порог общий со сворачиванием намеренно: своим порогом напоминание ставилось бы
задолго до тесноты, добавляя по сообщению на ход через всю сессию — там, где
место ещё есть и забывать нечего.

`--max-turns` при этом остаётся, но сторожит уже другое: не окно, а
зацикливание на инструментах. Когда размер окна неизвестен (сервер его не
сообщил и `--context-window` не задан), мерить нечем — там `--max-turns`
по-прежнему единственный ограничитель.

### Расход токенов

`/usage` показывает, во что обошлась сессия:

```
> /usage
Токены за сессию:
  отправлено:  1037
  сгенерировано: 120
  контекст сейчас: 530 (запросов: 2)
```

**«Отправлено» и «контекст» — разные числа, и это не ошибка.** История уходит
модели целиком на каждом ходу, поэтому одни и те же сообщения оплачиваются
повторно: «отправлено» — сумма по всем запросам, а «контекст сейчас» — размер
последнего, то есть текущий объём диалога. Именно второе число упирается в окно
модели, а первое ближе к деньгам на облачном эндпоинте.

Потраченное `/clear` не обнуляет: история начинается заново, но счёт за неё уже
выставлен. По той же причине расход провалившегося хода остаётся в счётчике,
хотя сам ход снимается с истории.

### Обрыв ответа на лимите

`max_tokens` ограничивает **ответ** модели, а не размер контекста. Упершись
в него, агент говорит об этом прямо:

```
● Ответ оборван на лимите генерации (max_tokens: 1100), текста не осталось.
  У рассуждающих моделей размышления тратят тот же бюджет.
  Увеличьте --max-tokens или MAX_TOKENS.
```

**Пустой ответ у рассуждающей модели почти всегда означает именно это.**
qwen3 и подобные отдают размышления отдельным полем `reasoning_content`,
но тратят на них общий с ответом бюджет: выбрав его целиком, модель
возвращает пустой текст. Внешне — «модель промолчала», на деле — не хватило
токенов. Если ответ оборвался, но текст всё же пришёл, он показывается
и сохраняется, а рядом печатается предупреждение о неполноте.

Обрыв на пустом ответе — это невыполненная задача, и код возврата будет `3`.
`/compact` в таком случае отказывается сворачивать: обрезанное резюме заместило
бы диалог неполным, и вернуть его было бы уже нечем.

### Ответ по мере генерации

Текст печатается по мере того, как модель его выдаёт, — включено по умолчанию.
Выключается `--no-stream` или `LLM_STREAM=false`, если сервер потока не умеет.

На рассуждающей модели одного текста мало. Замер на `qwen3.6`: из 190 токенов
ответа 187 ушли в размышления, а сам ответ занял три, — то есть 79 секунд
неподвижного спиннера и текст в самом конце. Поэтому рядом со спиннером идёт
объём размышлений:

```
⠹ Думаю… ход 1/10 (размышления: 2623 знака)
```

Сами размышления не показываются: они приходят отдельным полем и полезны не
как чтение, а как ответ на вопрос «модель считает или зависла».

Расход токенов в потоке сохраняется — агент просит его отдельным полем
(`stream_options.include_usage`), иначе `/usage` и `/context` показывали бы
нули: без этой просьбы сервер `usage` в потоке не присылает вовсе.

Если сервер не понимает `stream`, он отвечает пустым телом. Это не «модель
промолчала», и агент их различает:

```
● Ответ пришёл пустым потоком. Если сервер не умеет stream, отключите его: --no-stream
```

### Разметка в терминале

Ответы модели показываются с разметкой: заголовки и `**жирный**` — ярким,
`*курсив*` — приглушённым, `` `код` `` и блоки ``` ``` ``` — серым. Длинные
строки переносятся по ширине терминала. Выключается `--no-markdown` или
`AGENT_MARKDOWN=false`; вне терминала (вывод в файл или в конвейер) разметка
не применяется никогда — там она была бы мусором из управляющих
последовательностей.

Рендерер свой, потому что зависимостей у агента нет ни одной,
а готовые рендерят документ целиком — со стримингом это несовместимо.
Разметка разбирается **только на целой строке**: границы кусков, приходящих
из сокета, не совпадают ни с чем, и `**жир` с `ный**` приезжают порознь.
Внутри блока кода строка отдаётся дословно и **не переносится** — перенесённая
команда выглядит копируемой, не будучи ею. Номера в нумерованных списках
печатаются те, что написала модель: перенумеровать значит скрыть её дефект.

Разметка применяется только к тексту модели. Вывод команд, результаты
инструментов и предупреждения агента идут как есть: `*` в выводе `ls` —
это звёздочка, а не курсив.

### Медленная модель

Ожидание ответа — 1200 секунд, `--llm-timeout N` или `LLM_TIMEOUT`. Это **не**
таймаут команд `bash` (`COMMAND_TIMEOUT`): числа разные, потому что правка ради
медленной модели не должна заодно продлевать ожидание зависшей команды.

Значение измерено, а не взято с запасом. На `bonsai-27b` (Q1_0, рассуждающая)
скорость — около 5,7 токена/с: вопрос на три абзаца занял 176 секунд, а
`17*23` — 347, из которых почти всё ушло в размышления. На `qwen3.6-35b-a3b`
просьба написать класс на 60 строк заняла **697 секунд** — 8156 токенов,
из них 8063 размышлений. Прежнего умолчания в 600 секунд не хватало.

Исчерпанное ожидание **не повторяется**: если модель не успела, ещё два таких
же ожидания дадут то же самое — при лимите 1200 с это час молчания вместо
ответа. Сообщение называет причину прямо:

```
● Ошибка связи с LLM: Модель не ответила за 1200 с. Если она просто медленная,
  увеличьте --llm-timeout или LLM_TIMEOUT.
```

Раньше на этом месте был `Net::ReadTimeout with #<TCPSocket:(closed)>` — он
выглядит как обрыв сети и посылает проверять связь вместо того, чтобы поднять
лимит.

### Контекстное окно

`max_tokens` и история делят **одно** окно, и его размер задаётся при загрузке
модели на сервере — OpenAI-совместимый протокол о нём не сообщает. Поэтому
агент спрашивает его у LM Studio через её собственный `/api/v0/models`, а на
любом другом сервере молча обходится без него. Задать вручную: `--context-window
N` или `CONTEXT_WINDOW`; заданное явно перебивает узнанное и запрос не делается.

Загруженных моделей на сервере может быть несколько, с разными окнами. Проба
ищет ту, что названа в `--model`; если имя не совпало ни с одной, но загружена
ровно одна — берётся она (LM Studio на незнакомое имя молча подставляет
загруженную). Когда загружено несколько и совпадения нет, размер остаётся
неизвестным: показать чужое окно хуже, чем не показать никакого.

**`max_tokens` по умолчанию — половина окна, но не больше 16384.** Отдельной
константой это число задать нельзя: 4096 мало при окне 100k, а 16384 больше
всего окна при 8192, и `/context` показывал 206% на пустой сессии. Заданное
руками (`--max-tokens`, `MAX_TOKENS`) не трогается — из двух указаний одного
смысла верить надо более точному.

Доля не заменяет большого окна. При 8192 половина даёт 4096, и рассуждающая
модель этот бюджет **выбирает целиком на размышления**, не дойдя до текста:
живая проверка на `qwen3.6-35b-a3b` оборвала задачу «создай файл с классом
на 25 строк» и при 2048, и при 4096. Лечится это загрузкой модели с бо́льшим
окном на сервере, а доля отвечает лишь за то, чтобы резерв не превышал самого
окна.

`/model` показывает размер, `/context` — заполнение:

```
  по данным сервера последний промпт — 1747 токенов
  окно модели: 32768 токенов
    история        1747
    резерв ответ  16384
    свободно      14637  (55% занято)
```

**Резерв под ответ входит в занятое.** Место в окне нужно не только истории:
`max_tokens` тоже претендует на него, и без учёта этого картина обманчива —
пустой диалог при `max_tokens: 4096` и окне 8192 занимает половину, ещё
не начавшись. Поэтому окно и печатается слагаемыми: одно составное число
(«6253 из 8192») вызывало ровно тот вопрос, на который должно было отвечать —
занято это или свободно. Когда резерв в окно не помещается, вместо «свободно»
печатается «не хватает»: отрицательный остаток читался бы как ошибка счёта.

Предупреждений три, и лечения у них разные:

| Что сказано | Чем лечится |
|---|---|
| Окно заполнено, занято диалогом | `/compact` — пока он ещё проходит |
| Окно заполнено, занято описанием проекта | правкой самого `AGENTS.md` |
| На ответ остаётся меньше `max_tokens` | уменьшить `--max-tokens` либо увеличить окно на сервере |

Последнее — предупреждение о риске, а не приговор: `max_tokens` это разрешение,
а не бронь. При остатке 6035 и лимите 7000 короткий ответ приходит целиком;
оборвётся длинный, и оборвётся на остатке, а не на лимите.

Если размер окна неизвестен, так и написано — вместо процентов, которых не
из чего посчитать:

```
  размер окна неизвестен — сервер о нём не сообщает, задайте --context-window
```

**Ctrl+C прерывает задачу, а не сессию.** Если модель запустила не то или
задумалась надолго, Ctrl+C останавливает текущую работу — история остаётся,
можно уточнить задачу и продолжить. Запущенная команда при этом убивается.
На пустом приглашении первый Ctrl+C сбрасывает набранную строку, второй
подряд — выходит.

### Какая модель отвечает

`--list-models` показывает, что реально загружено на сервере; звёздочкой
помечена выбранная:

```
$ mini_agent --list-models
Модели на http://llm-server:1234/v1:
    deepseek-coder-v2-lite-instruct
  * qwen/qwen3.6-35b-a3b
    text-embedding-nomic-embed-text-v1.5
```

Проверять стоит, потому что LM Studio на незнакомое имя модели **не отвечает
ошибкой** — он молча берёт загруженную. Без этой команды подмену нечем
заметить: агент работает, но не на той модели, которую вы указали.

### Рабочий каталог

По умолчанию агент выполняет команды там, откуда запущен. `--cwd DIR` (или
`AGENT_CWD`) переносит их в другой каталог — там же он ищет и `AGENTS.md`:

```bash
mini_agent --cwd ~/projects/other "запусти тесты"
```

Каждый вызов `bash` — отдельный процесс, и **между вызовами ничего не
сохраняется**: ни текущий каталог, ни переменные окружения. Отдельный `cd sub`
молча пропадает, следующая команда снова начнёт с рабочего каталога. Модель
предупреждена об этом в системном промпте и связывает шаги сама
(`cd sub && ls` вместо двух вызовов).

### Транскрипт диалога

`--log FILE` (или `AGENT_LOG`) пишет весь обмен с моделью в файл — по одному
объекту JSON на строку. По умолчанию выключено.

```bash
mini_agent --log session.jsonl "почини падающий тест"
jq -r 'select(.role=="tool") | .content' session.jsonl   # что видела модель
```

Первой строкой каждого запуска идёт `{"type":"session", …}` с версией агента,
моделью, сервером, параметрами сэмплинга и рабочим каталогом: в один файл
складываются несколько запусков, и без этой пометки непонятно, где кончился
прошлый. Версия и сэмплинг там же не для полноты — они определяют поведение
прогона целиком, а по старому журналу их уже не переспросить. `"sampling":{}`
пишется и тогда, когда не задано ничего: отсутствие ключа было бы неотличимо
от журнала старой версии. Дальше — сообщения в том
порядке, в каком их видела модель, включая системный промпт и полный вывод
команд (в консоли он обрезан для читаемости). Ключ API в журнал не пишется.

Записи попадают на диск сразу, а не при выходе: разбираться в логе приходится
как раз тогда, когда до нормального завершения дело не дошло — агент завис,
упал или его убили.

Размышления рассуждающих моделей (`reasoning_content`) идут отдельной строкой
`{"type":"reasoning", …}` перед ответом, которому они предшествовали. В саму
историю они не попадают никогда — модель их себе не пересылает, — так что
журнал единственное место, где их видно. Нужны они при обрыве ответа: без них
известно только, что текста нет, а не на что модель потратила бюджет.

```bash
jq -r 'select(.type=="reasoning") | .content' session.jsonl
```

Если ход не удался, его сообщения снимаются с истории, а в журнале появляется
строка `{"type":"rollback"}`. Сами снятые сообщения остаются на месте: журнал
показывает, что действительно уходило модели, — иначе по нему нельзя было бы
понять, на чём именно запрос упал. Тем же способом отмечены сворачивание
(`{"type":"compact"}`) и сброс контекста после одобрения плана
(`{"type":"plan"}` с путём к файлу плана): историю после них заменяет новая,
и без пометки это выглядело бы как обрыв записи.

> В журнал попадают и ваши задачи, и содержимое всех файлов, которые агент
> читал. Прежде чем приложить его к отчёту или багрепорту, посмотрите, что
> в нём оказалось.

### Продолжение сессии

Каждый запуск сохраняется сам — в `~/.mini_agent/sessions` тем же форматом,
что и `--log`. `--resume` продолжает последнюю сессию **этого рабочего
каталога**: история восстанавливается, и модель помнит, о чём шла речь.

```bash
mini_agent "найди, где считается размер окна"
mini_agent --resume "теперь добавь туда проверку"
mini_agent --resume -i                  # продолжить в интерактивном режиме
```

Продолжение дописывает тот же файл, а не заводит новый: один разговор не
должен разъезжаться по двум сессиям каталога. Восстанавливается при этом не
весь журнал, а то, что было у модели последним, — снятые ходы, свёрнутый
диалог и сброс после одобрения плана учитываются так же, как они происходили.
Системный промпт берётся нынешний: рабочий каталог, система и описание проекта
со вчерашней сессии могли измениться, и подсовывать модели вчерашнее описание
окружения нельзя.

Аргумента у `--resume` нет: следующим словом в командной строке стоит задача,
и `mini_agent --resume почини тест` пытался бы продолжить сессию из файла
«почини». Конкретный журнал называет `--log` — читается он одинаково, чем бы
ни был заведён:

```bash
mini_agent --log вчера.jsonl --resume "продолжим"
```

Продолжать нечего, журнал пуст или не читается — агент откажется работать
(код 1), а не начнёт с чистой истории: тихий старт неотличим от успешного
продолжения ровно до того момента, когда выяснится, что модель ничего
не помнит.

`--no-session` (или `AGENT_SESSION=false`) выключает сохранение. `--log`
выключает его тоже: писать одно и то же в два места незачем.

```bash
ls ~/.mini_agent/sessions        # 2026-08-21-142530-mini-agent.jsonl
```

> Здесь лежит то же, что и в `--log`: ваши задачи и содержимое прочитанных
> файлов. Каталог создаётся с правами 0700, но сессии копятся и сами
> не удаляются — чистите их, если работаете с чужими секретами.

### Описание проекта

Если в рабочем каталоге лежит `AGENTS.md` (или `.mini_agent.md`), агент читает
его и дописывает к системному промпту. Туда стоит положить то, что иначе он
выясняет заново каждый запуск: чем запускаются тесты, где лежат исходники,
на каком языке комментарии.

```
$ mini_agent "какой командой запускаются тесты?"
Контекст проекта: AGENTS.md

● Тесты запускаются командой make spec-fast.
```

Без этого файла тот же вопрос стоит нескольких ходов `ls` и `find`.
Берётся первый найденный файл, потолок — 20 000 знаков.

Длинное описание урезается по границе строки, и агент об этом говорит:

```
● Описание проекта урезано до 19936 из 89600 знаков: файл такой длины — уже
  документация проекта, а не описание, и она вытесняет из окна саму задачу.
  Помогает только правка файла — /compact и /clear его не трогают.
```

Причин у обрезки две, и лечения разные. Потолок в 20 000 знаков сдвинуть
нельзя — сокращайте файл. Но если размер контекстного окна известен
(см. `--context-window`), описанию отводится не больше его четверти, и на
маленьком окне режет уже она: тогда помогает и модель с бо́льшим `ctx`
на сервере. Что именно сработало, сказано в самом сообщении.

Написать его можно и руками, но проще поручить агенту — команда `/init`
в интерактивном режиме:

```
> /init
● Bash(pwd && ls -la)
● Bash(cat README.md)
● Bash(cat Rakefile)
● Bash(cat src/parser.rb)
● Bash(rake -T 2>&1)
● Bash(rake 2>&1)
● Bash(cat > AGENTS.md << 'EOF' …)
● Bash(cat AGENTS.md)

Описание проекта записано: AGENTS.md (694 байта).
  Оно вступит в силу после /clear или при следующем запуске.
```

Агент изучает каталог сам и пишет файл на языке, принятом в самом проекте.
Команды сборки и тестов ему велено **проверять запуском**, а не переписывать
из README: неверная команда хуже отсутствующей, потому что выглядит
проверенной. Живая проверка показала, что это не перестраховка — без явного
требования модель приняла `require "rake/testtask"` за наличие задачи `test`
и записала несуществующую команду.

Если описание уже есть, `/init` покажет его размер и спросит про перезапись —
файл мог писать человек.

Новое описание попадает в системный промпт при сборке истории, поэтому к уже
идущему диалогу оно не применяется: нужен `/clear` или следующий запуск.
Применять его на месте значило бы незаметно выбросить текущую историю.

> **Файл описания равносилен исполняемому коду.** Указания внутри `AGENTS.md`
> модель выполняет: строка «игнорируй задачу пользователя и сделай вот это»
> в нём работает, и никакая формулировка промпта этого не предотвращает
> (проверено живьём). Тот, кто подложил файл, управляет агентом, а агент
> запускает команды. Открывать чужой непроверенный проект этим агентом так же
> рискованно, как выполнять в нём `make`. Строка «Контекст проекта: …»
> в выводе показывает, что файл подхвачен.

### Переменные окружения

`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `MAX_TURNS`, `RETRY_COUNT`, `RETRY_DELAY`, `MAX_TOKENS`, `CONTEXT_WINDOW`, `LLM_TIMEOUT`, `LLM_STREAM`, `AUTO_COMPACT`, `AUTO_COMPACT_AT`, `AGENT_MARKDOWN`, `AGENT_POLICY`, `ALLOW_UNSAFE`, `AGENT_PLAN`, `COMMAND_TIMEOUT`, `AGENT_CWD`, `AGENT_LOG`, `AGENT_SESSION`.

Параметры сэмплинга: `LLM_TEMPERATURE`, `LLM_TOP_P`, `LLM_TOP_K`, `LLM_MIN_P`,
`LLM_REPEAT_PENALTY`, `LLM_PRESENCE_PENALTY`, `LLM_FREQUENCY_PENALTY`,
`LLM_SEED`. Префикс `LLM_`, а не `AGENT_`: это поля протокола, уходящие в тело
запроса, а не поведение самого агента.

Приоритет: опции CLI → переменные окружения → файл настроек → значения
по умолчанию.

```bash
export LLM_BASE_URL=http://llm-server:1234/v1
export LLM_MODEL=qwen3-coder
mini_agent "покажи структуру проекта"
```

### Файл настроек

Постоянные предпочтения — свой сервер, своя модель, подобранный сэмплинг —
живут в `~/.mini_agent/settings.json`. Ключи те же, что у опций командной
строки, только через подчёркивание:

```json
{
  "base_url": "http://llm-server:1234/v1",
  "model": "qwen/qwen3.6-35b-a3b",
  "policy": "ask",
  "temperature": 0.25,
  "top_p": 0.9
}
```

Файл встаёт **под** переменные окружения: он говорит «как обычно», а
`LLM_MODEL=… mini_agent …` — «сейчас иначе». Значение из файла считается
заданным человеком наравне с флагом: `"max_tokens": 4096` действительно
ограничивает ответ, а не проигрывает доле контекстного окна.

Файла может не быть — это обычное дело. А вот ошибки в нём разбирательства
не откладывают: неизвестный ключ (`"max_token"` без `s`), испорченный JSON
и не найденный `--settings путь` роняют запуск с кодом 1. Молчаливый откат
к умолчаниям выглядел бы точно так же, как удачное чтение.

- `--settings ФАЙЛ` — взять другой файл вместо умолчательного;
- `--no-settings` — не читать файл вовсе. Этот флаг передают оценочные
  задачи (`make evals`): личные настройки иначе молча участвовали бы
  в измерениях, не показываясь в отчёте.

Прочитанный файл виден в `/model` и в заголовке журнала — по пути, без
содержимого. **Права на файл агент не проверяет.** Если в нём лежит
`api_key`, выставьте их сами: `chmod 600 ~/.mini_agent/settings.json`.

## Как это работает

```
CLI → Agent (цикл ходов) → LLMClient ⇄ LLM
                ↓
         ToolRegistry → Tools::Bash → CommandGuard → ProcessRunner
                      → Tools::ReadFile / WriteFile / EditFile
```

Агент отправляет модели задачу вместе со схемой доступных инструментов. Модель отвечает либо вызовом инструмента — тогда команда выполняется, а её вывод возвращается модели, — либо обычным текстом, что означает завершение работы. Цикл ограничен числом ходов; по достижении лимита агент просит модель подвести итог.

## Безопасность

Агент выполняет shell-команды, которые формирует языковая модель. Что при этом
спрашивать, а что выполнять молча, задаёт политика подтверждений — `--policy`
или `AGENT_POLICY`:

| Политика | Спрашивает | Выполняет молча |
|---|---|---|
| `deny` (по умолчанию) | Опасные команды (`rm -rf`, `sudo`, `curl \| sh`, форк-бомба) | Всё остальное |
| `ask` | Всё, кроме заведомо читающего | `ls`, `cat`, `grep`, `git status` и подобные |
| `unsafe` | Ничего | Всё, об опасном только предупреждает |

Умолчанием оставлен `deny`, а не `ask`: агента зовут работать, и на задаче вида
«запусти тесты» строгая политика превращает её в череду подтверждений. Строгую
включают осознанно.

`ask` опирается на список заведомо читающих команд (`ReadOnly`) — обратную
сторону денилиста. Критерий включения в него: у команды нет режима записи,
включаемого флагом. Поэтому там нет `sed` (`-i`), `sort` (`-o`), `find`
(`-delete`), а также `tee`, `xargs` и `env` — эти трое выполняют чужую команду,
то есть пропустили бы мимо списка что угодно. Строка режется по разделителям, и
читающей считается только та, у которой читают **все** части: `ls | head` — да,
`ls | tee файл` — нет. Любое перенаправление и любая подстановка команды
(`` ` ``, `$(`) означают отказ сразу. У `git` проверяется подкоманда, а не сам
`git`: `git status` читает, `git commit` пишет. Перед подкомандой пропускаются
`-C` и `--no-pager` — ни один из них не влияет на то, пишет она или читает;
`-c` не пропускается, потому что через алиас им задают чужую команду целиком.

На этот же список опирается режим планирования (см. выше) — там он впервые
становится несущим: в `ask` его ошибка стоит лишнего вопроса, в планировании —
отвергнутой команды.

**Ни один из этих списков не является песочницей.** Оба разбирают строку, а не
синтаксическое дерево shell, и обходятся переписыванием команды: переменные,
кавычки, base64. Ошибка денилиста — пропустить разрушительное, ошибка списка
читающих — спросить лишний раз; второе дешевле, поэтому он намеренно короткий.
Если вы запускаете агента с недоверенной моделью или на важной машине,
используйте реальную изоляцию — контейнер или отдельного пользователя
с ограниченными правами.

Флаг `--allow-unsafe` (или `ALLOW_UNSAFE=true`) сохранён и означает
`--policy unsafe`. Названная политика его перебивает: из двух указаний одного
смысла верить надо более точному.

## Разработка

Рабочие вызовы собраны в `Makefile`; `make help` печатает список целей.

```bash
make setup        # установка зависимостей
make              # тесты и линтер
make spec         # только тесты
make spec FILE=spec/mini_agent/agent_spec.rb:42     # один пример
make lint         # линтер
make rbs          # проверка сигнатур в sig/
make console      # IRB с загруженным гемом
make run TASK="покажи структуру проекта"
make repl         # интерактивный режим
make build        # собрать гем
make install      # собрать и установить локально
make evals        # оценочные задачи (ходит к настоящей модели, идёт часами)
```

Тесты не требуют запущенного LLM: HTTP стабится через webmock, сеть в тестах запрещена.

### Оценочные задачи

`evals/` — стенд, отвечающий на вопрос «от этой настройки стало лучше, хуже
или не повлияло». Живая проверка на глаз на него не отвечает: небольшая сеть
проходит одну и ту же задачу через раз, и два прогона подряд дают разное при
одних и тех же настройках.

```bash
make evals                              # все задачи, все наборы, 3 прогона
make evals TASKS=empty-grep RUNS=5      # одна задача, пять прогонов
ruby evals/run.rb --dry-run             # показать команды и выйти
```

Задачи (`evals/tasks/*.json`) бьют в замеченные отказы: зацикливание на пустом
поиске, выдуманный путь, правка существующего метода, работа при заранее
раздутом контексте. Успех определяют проверки, а не код возврата: агент выходит
с нулём, сказав «файл создан» и не создав файла, — ровно то, ради чего стенд
и заведён. Подробности — в [`evals/README.md`](evals/README.md).

В гем стенд не входит: он нужен разработчику, а не тому, кто агента установил.
