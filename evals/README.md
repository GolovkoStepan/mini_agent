# Оценочные задачи

Стенд, отвечающий на один вопрос: **от этой настройки стало лучше, хуже или не
повлияло?** Живая проверка «на глаз» на него не отвечает — небольшая сеть
проходит одну и ту же задачу через раз, и два прогона подряд дают разный
результат при одних и тех же настройках.

В гем стенд не входит (`spec.files` отбрасывает `evals/`): он гоняет агента
десятками прогонов и нужен разработчику, а не тому, кто агента установил.

## Запуск

```bash
make evals                                   # все задачи, все наборы, 3 прогона
make evals TASKS=empty-grep RUNS=5           # одна задача, пять прогонов
make evals PRESETS=server,tuned              # только эти наборы
make evals ARGS="--model qwen3-coder"        # флаги после ARGS уходят агенту
ruby evals/run.rb --dry-run                  # показать команды и выйти
```

**Это часы, а не минуты.** При ~6 токенах в секунду одна мелкая задача идёт
минутами, а матрица — это задачи × наборы × прогоны. Начинайте с `--dry-run`:
убедиться, что модель и адрес те самые, дешевле до запуска, чем после.
Прерывание (Ctrl+C) не теряет сделанного — печатается отчёт по тому, что успели.

## Задача (`tasks/*.json`)

```json
{
  "name": "empty-grep",
  "about": "зацикливание на пустом поиске",
  "prompt": "найди в проекте функцию calculate_tax и скажи, где она",
  "setup": ["mkdir -p lib", "printf '...' > lib/a.rb"],
  "checks": ["grep -qiE 'не найд|отсутств' ../answer.txt"],
  "max_turns": 6
}
```

`setup` готовит фикстуру, `checks` — команды, которые обязаны вернуть 0. Обе
идут в рабочем каталоге прогона; ответ модели лежит на уровень выше
(`../answer.txt`) — иначе он попадал бы в проверки вида «сколько файлов в
каталоге».

**Успех определяют проверки, а не код возврата агента.** Агент выходит с нулём,
сказав «файл создан», и не создав файла, — ровно то фантазёрство, ради которого
стенд и заведён.

Задачи бьют в замеченные отказы: пустой поиск (зацикливание), выдуманный путь,
правка существующего метода, запись нового файла, работа при заранее раздутом
контексте. Неизвестное поле в JSON роняет запуск: `"check"` вместо `"checks"` —
это молча не работающая задача, которая проходит каждый прогон.

## Набор (`presets/*.json`)

```json
{ "about": "вчерашний набор из LM Studio", "temperature": 0.3, "repeat_penalty": 1.12 }
```

Ключи — параметры сэмплинга агента один в один (`Sampling::KEYS`). Пустой набор
(`server.json`) — это «решает сервер», исходный уровень сравнения: `Report`
берёт за основу первый по алфавиту.

**Зерна в наборе нет.** Оно принадлежит прогону: попытка *i* получает
`seed + i`, одинаково для всех наборов. Задай его набор — каждый получил бы свою
последовательность случайности, и к разнице настроек примешалась бы разница
случайности. `--no-seed` отключает зерно вовсе.

## Отчёт

Три части: доля успехов по задачам, средний расход (ходы, вызовы, повторы,
токены, секунды) и вердикт по каждому набору относительно исходного.

Расход усредняется **только по успешным прогонам**: провал обычно короче
успеха, и в общей куче набор с большим числом провалов выглядел бы самым
экономным.

Вердикт — не сравнение двух чисел. Разница объявляется значимой, только если
она вдвое перекрывает разброс (нормальное приближение со сглаживанием
Агрести — Коулла: без него набор, прошедший все прогоны, даёт нулевой разброс,
и перевес в один прогон объявляется несомненным). Пока прогонов меньше
`Evals::MIN_OBSERVATIONS`, вердикт — «мало наблюдений», и это отдельное
состояние от «не повлияло»: незнание и равенство — разные ответы.

## Каталог прогона

`evals/results/<набор>/<задача>/<попытка>/`:

| | |
|---|---|
| `work/` | рабочий каталог агента: фикстура и то, что он с ней сделал |
| `log.jsonl` | журнал агента (`--log`) — отсюда берутся ходы, токены, повторы |
| `answer.txt` | что агент напечатал |
| `stderr.txt` | ошибки |

Каталог прошлого прогона сносится, а не дополняется: оставленный файл прошлой
попытки прошёл бы проверки этой, ничего не делая.

Сводка всех прогонов — `evals/results/results.json`.

## Устройство

| Класс | Ответственность |
|---|---|
| `Task` | Задача из JSON: подготовка, задание, проверки |
| `Preset` | Набор параметров сэмплинга → флаги агента |
| `Runner` | Один прогон: каталог, подготовка, запуск агента, проверки |
| `Journal` | Метрики из журнала агента |
| `Result` | Исход одного прогона |
| `Report` | Таблицы и вердикт |

`Runner` запускает **настоящий `exe/mini_agent`** отдельным процессом, а не
собирает `Agent` в памяти: разбор флагов, сборка промпта и коды возврата — часть
измеряемого. Стенд, зовущий внутренности, померил бы не то, чем пользуются.

Спеки стенда лежат в `spec/evals/` и идут обычным `make spec` (`spec_helper.rb`
добавляет `evals/lib` в путь загрузки). Сеть в них не нужна: агент запускается с
`--version`, разбирает все флаги и выходит, не открывая соединения.
