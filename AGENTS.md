# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

Комментарии в коде, сообщения пользователю и документация в этом проекте — на русском языке. Имена классов, методов и переменных — на английском. Придерживайтесь этого разделения.

## Что это

Консольный агент, решающий задачи программирования: отправляет запрос в LLM по OpenAI-совместимому протоколу, получает вызовы инструментов, выполняет их и возвращает результат модели. Инструменты: `bash` и три файловых — `read_file`, `write_file`, `edit_file`. Рассчитан на локальный сервер (LM Studio, Ollama), но работает с любым эндпоинтом `/chat/completions`.

## Документация

Дополнительная информация — в каталоге `docs/`:

- `docs/DECISIONS.md` — обоснования решений, не видные из кода (в `AGENTS.md` от них оставлены только сквозные инварианты);
- `docs/ROADMAP.md` — план развития.

Отдельно есть `evals/README.md` про оценочные задачи.

## Команды

Все рабочие вызовы собраны в `Makefile` — используйте его, а не голые `bundle exec`. `make help` печатает список целей.

```bash
make setup                     # установка зависимостей
make                           # spec + rubocop (цель по умолчанию)
make spec                      # только тесты
make spec FILE=spec/mini_agent/agent_spec.rb      # один файл
make spec FILE=spec/mini_agent/agent_spec.rb:42   # один пример по строке
make lint                      # только линтер
make rbs                       # проверка сигнатур в sig/

make run TASK="покажи содержимое lib"             # разовый запуск
make run TASK="запусти тесты" ARGS="--model qwen3-coder"
make repl                      # интерактивный режим
make build                     # сборка гема

make evals                     # оценочные задачи на живой модели (часы!)
make evals TASKS=empty-grep PRESETS=server,tuned RUNS=3
```

`make evals` ходит к настоящей модели и в `make check` не входит намеренно — см. `evals/README.md`.

`make check` эквивалентен `rake`: `Makefile` ничего не дублирует, а только оборачивает `rake`/`rspec`/`rubocop` с правильными флагами.

**Новый файл в `lib/` не попадёт в собранный гем, пока не добавлен в индекс git.** `spec.files` в `mini_agent.gemspec` берётся из `git ls-files`, и неотслеживаемый файл она не видит. Локально это не проявляется: `bundle exec` и `make spec` читают с диска. Ломается только установленный гем — `cannot load such file` на первом же `require_relative`. Перед `make build` делайте `git add`, а после установки проверяйте гем из чужого каталога, а не из этого.

Настройки читаются в порядке: **опции CLI → переменные окружения → файл `~/.mini_agent/settings.json` → значения по умолчанию** (`Config::DEFAULTS`). Переменные: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `MAX_TURNS`, `RETRY_COUNT`, `RETRY_DELAY`, `MAX_TOKENS`, `CONTEXT_WINDOW`, `LLM_TIMEOUT`, `LLM_STREAM`, `AUTO_COMPACT`, `AGENT_POLICY`, `ALLOW_UNSAFE`, `COMMAND_TIMEOUT`, `AGENT_CWD`, `AGENT_LOG`, `AGENT_SESSION`.

Адрес LLM по умолчанию — `http://llm-server:1234/v1`. Имя `llm-server` должно быть прописано в `/etc/hosts` (см. README): сервер обычно стоит на отдельной машине, и жёсткий IP в репозитории быстро устаревает. Для живых проверок сначала убедитесь, что имя резолвится: `curl http://llm-server:1234/v1/models`.

## Архитектура

Поток управления: `exe/mini_agent` → `CLI` (разбор опций) → `AgentBuilder` (сборка объектов) → `Agent#run` (цикл ходов) → `LLMClient#chat` ↔ `ToolRegistry#dispatch` → `Tools::Bash` / `Tools::ReadFile` / `Tools::WriteFile` / `Tools::EditFile` → `CommandGuard` + `ProcessRunner`.

| `AgentBuilder` | Сборка агента с зависимостями на время одного запуска |

| `Connection` | Соединение с сервером: поднять, держать, погасить; таймауты |
| `ErrorResponse` | Разбор неуспешного ответа: повторять ли, сколько ждать, что показать |

### Инварианты

Полные обоснования каждого решения — в `docs/DECISIONS.md`, рядом с кодом — в комментариях и тестах. Здесь остаются только сквозные правила: они ломаются молча и не привязаны к одному файлу.

- **`Agent#run` возвращает `Conversation`, а не текст** — на этом держится продолжение диалога между задачами.
- **Прерывание построено на `Interrupt`, а не на флаге из `trap`** (флаг не рвёт блокирующее чтение сокета). Любой `rescue Exception` ломает его молча.
- **`Conversation#push` — единственное место, через которое проходят все сообщения;** журнал зовётся оттуда.
- **`History` — одна точка сборки новой `Conversation`:** новое поле истории добавляйте в `History`, иначе оно теряется после `/clear` и `/compact`.
- **Итог работы и код возврата — разные вещи:** `Agent#outcome` (код 4 отдельный), `Agent#failed?` — для `Repl`.
- **Два независимых бюджета вывода** (`ToolCallRunner::SHARE` — в модель, `UI::PREVIEW_*` — человеку) не объединять.
- **`Messages::Tool` — данные для модели:** эмодзи там не возвращать, оформление живёт в терминальном слое.
- **Формат и его разбор меняются вместе и стоят рядом** (`EXIT_CODE`/`EXIT_CODE_PATTERN`, шапка плана).
- **`UI#tool_result` режет только переводы строк (`\A\n+`, `\n+\z`),** а не `strip` — иначе ломается выравнивание колонок.
- **Журнал — протокол, а не состояние:** `Transcript` пишет по сообщению с `sync = true`; `rollback`/`compact` не переписывают лог, а дописывают; токены неудачного хода не откатываются.
- **Сохранённая сессия — тот же журнал:** `--resume` продолжает любой лог (в том числе снятый `--log`), системный промпт берётся нынешний, продолжение дописывает тот же файл.
- **`usage` идёт в журнал, но не в сообщение;** `push(role:, content:)` без скобок Ruby читает как keyword-аргументы — в историю уйдут пустые сообщения.
- **`Usage` складывает только токены генерации;** осмысленно последнее значение `prompt_tokens` — текущий размер контекста.
- **`/context` меряет знаки, а `/compact` работает на упреждение** — переполненный контекст он не лечит.
- **`max_tokens` считается от окна долей (`Window::SHARE`), а не задаётся числом.** `WARN_AT = 0.75` опускать безопасно, поднимать нет; `CHARS_PER_TOKEN = 2.5` — оценка снизу, менять только вниз.
- **Каждый `tool_call_id` обязан получить ответ** (`ToolCallRunner#call_all`/`#abandon`), иначе дыра валит следующий запрос; счёт повторов сбрасывается на задачу.
- **Число в промпте и число в коде — одно:** `SYSTEM_PROMPT` — шаблон (`Messages.system_prompt`).
- **Охрана получает `read_only:` от самого инструмента,** а не разбирает строку. Два списка (`DANGEROUS_PATTERNS` и `ReadOnly`) не сливать; порядок в `verdict`: планирование → денилист → читающие.
- **`Config#allow_unsafe?` — вопрос к политике,** а не отдельное поле. От `Lookup#given?` зависят `max_tokens_derived?` и выбор политики — новый ключ без умолчания проверяйте по обеим.
- **Настройки:** файл — четвёртый источник в `Lookup#given`, белый список ключей — из `Config::ENV_KEYS`; незаданный параметр сэмплинга отсутствует в теле запроса (`fetch(:temperature)` падает `KeyError`).
- **`ProcessRunner`:** своя группа процессов, чтение `readpartial`, U+FFFD вместо негодных байт, без `Timeout.timeout`.
- **Стриминг:** кодировку назначает `feed` собранной строке; `include_usage` обязателен; пустой поток — не пустой ответ.
- **Экранируется только текст модели** (`UI#assistant`/`#stream_chunk`/`#ticker=`); вывод команд — нет.
- **Внедрение зависимостей ради тестируемости** (`UI.new(tty: false)`, `prompt:`, `timeout:`) сохраняйте; тест на прерывание обязан мерить время, а не только следствие.

## Тесты

`bundle exec rspec` — 988 примеров, ~14 секунд (тесты прерывания и фоновых потомков ждут настоящие процессы). HTTP стабится через **webmock**, сеть запрещена (`WebMock.disable_net_connect!`), живой LLM для тестов не нужен. `Config` принимает `env:` явно, а `spec_helper` подменяет `Settings::PATH` — тесты не зависят ни от окружения разработчика, ни от его домашнего каталога.

Тесты `ProcessRunner` запускают настоящие процессы (таймаут, убийство, вывод на 20 000 строк) — это осознанно: моки здесь не проверили бы ровно то, ради чего класс написан.

## Безопасность

Два списка поверх строки, которую **составляет сама модель**: `CommandGuard::DANGEROUS_PATTERNS` перечисляет заведомо разрушительное, `ReadOnly::COMMANDS` — заведомо читающее. Что делать с тем, что не попало ни в один, решает политика `--policy` / `AGENT_POLICY`: `deny` (умолчание) выполняет молча, `ask` спрашивает, `unsafe` не спрашивает вовсе. У файловых инструментов роль денилиста играет путь: запись за пределы рабочего каталога спрашивается при любой политике, кроме `unsafe`.

**Ни один из списков песочницей не является**: оба разбирают строку, а не синтаксическое дерево shell, и обходятся переписыванием команды — переменные, кавычки, base64. При работе с недоверенной моделью или недоверенным эндпоинтом нужна реальная изоляция (контейнер, отдельный пользователь), а не эти фильтры. `--allow-unsafe` / `ALLOW_UNSAFE=true` сохранены и означают `--policy unsafe`. Режим планирования (`/plan`, `--plan`) стоит поверх политики и опирается на тот же `ReadOnly` — со всеми его границами: песочницей он тем более не является и защищает от самодеятельности модели, а не от злого умысла.
